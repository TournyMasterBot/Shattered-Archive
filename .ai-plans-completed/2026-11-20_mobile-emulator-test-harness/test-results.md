Nothing was typed into any login form; no credential was read or used.
Results (all measured on `emulator-5554`, the physical phone attached throughout and never addressed: every `adb` call carried `-s emulator-5554`):
1. **Name resolution (box 1.2): the dev names do NOT resolve to this machine inside the emulator.** `auth.shatteredarchive.dev`, `shatteredarchive.dev` and `game-client.shatteredarchive.dev` all resolved to one public address that is not this machine (the Windows hosts file maps them to loopback on the host only). `example.com` resolved normally. So a login typed on the emulator against the hub's name would go to a real remote host unless the browser is made to map the name. A bind-mounted hosts file over `/system/etc/hosts` (the image is rootable: `adb root` works) changed the file but not the lookups: a name present only in that file stayed "unknown host". Undone (`umount`).
2. **Port mapping (box 1.3):** `adb reverse` for 5000, 80, 443 and 8081 succeeds and lists. The app's own request to `localhost:5000` reached the local C# container: its log shows `GET /api/world-map/index` during the test.
3. **Certificate (box 1.4): no authority needs installing.** The edge certificate is issued by the local mkcert authority and is valid for `*.shatteredarchive.dev`. Chrome on the emulator (113, `com.android.chrome`) reads `/data/local/tmp/chrome-command-line` because the image is debuggable (`ro.debuggable=1`). With `--host-resolver-rules="MAP *.shatteredarchive.dev 127.0.0.1"` and `--ignore-certificate-errors-spki-list=<sha256 of the edge certificate's public key, base64>` (computed at run time from `deploy/nginx/certs/shatteredarchive.dev.pem`) plus `--no-first-run --disable-fre --no-default-browser-check`, Chrome loaded `https://auth.shatteredarchive.dev/` from this machine's hub with a padlock (capture `phase-01_hub-login.png`, a notification prompt of Chrome over the page, fields empty). The file takes effect after `am force-stop com.android.chrome`.
4. **Unlock:** after the cold boot the user storage was locked: Chrome's activities did not resolve ("unable to resolve Intent") until the lock screen was passed with the emulator's PIN from the owner's notes. The tool must unlock before it starts a browser.
5. **Driving the browser (box 1.5): the debugging connection works.** `adb forward ... localabstract:chrome_devtools_remote` answers `/json/version` (Chrome 113); Playwright `connectOverCDP` attached, listed the open tabs, and read the hub page: title "Account – Shattered Archive", 2 inputs (1 password), buttons "Log in", "Need an account? Sign up", "Forgot password?". The password therefore never needs to go on a command line (Playwright `fill` goes over the debugging socket). A Custom Tab opened by the app appears in `/json` as a page with its URL. Two stale tabs from earlier sessions (map pages at the emulator's host alias) were present: the tool must not assume an empty browser.
6. **The app (box 1.6):** the already installed debug dev client (Expo SDK 58, React Native 0.88.1, Android 14) runs against a Metro started with the dev settings; Metro puts every `EXPO_PUBLIC_*` of its own environment into the bundle (checked in the fetched bundle: `EXPO_PUBLIC_WORLD_MAP_API` = the localhost value), so a setting passed to the process that runs Metro reaches the app. The app's cleartext request to `localhost:5000` works in this build (item 2). `start-android.js` inherits the environment (`scripts/start-android.js:160-163`), not re-run here because the app was already installed.
7. **What happened without Phase 3 (a mistake to own, and the finding it produced):** the app does not yet read `EXPO_PUBLIC_SITE_API`, so tapping Log in opened a browser session at the PRODUCTION site's sign-in start, which redirected to the hub name with the production callback address (`redirect_uri=https://shatteredarchive.com/user/game-sso/callback`). One unauthenticated GET therefore reached the production site, before any credential existed or was typed; the session was closed with Back, nothing was signed in. This is exactly the risk TESTENV-01 names, and it also shows the hub name `auth.shatteredarchive.dev` is shared: production's own sign-in redirects to it, so which hub a browser reaches is decided only by name resolution.
