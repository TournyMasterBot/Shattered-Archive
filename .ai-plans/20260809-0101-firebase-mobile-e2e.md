# Plan: Firebase (Analytics/Crashlytics/Push) + admin announcements + standalone mobile E2E testing

Created: 2026-08-09T01:01:00Z · Workspace: /workspace/shatteredarchive-mobile ·
Status: ACTIVE
Task: Wire Firebase Analytics/Crashlytics/Push (Android only) into the mobile app, add
a general Owner/Admin-only free-form announcement broadcast system to
Server.Web.Public (audit-logged, with "restart is coming" as just its default/common
template — not a separate code path), and build a standalone Maestro-based E2E tool
(in Shattered-AI/tools, not part of the app's own build) driving the Android emulator.

## Goal

Android builds of `shatteredarchive-mobile/dsl-client` report Analytics events and
native crashes to Firebase, and register an FCM token with the DSL web server on login.
An Owner/Admin-only page on the website can send a free-form push announcement to every
registered device — every send is itself an audit-log entry (who, what, when, delivery
counts), listable by Owner/Admin only. "Restart is coming" is just a quick-fill template
button on that page, not a special-cased feature. A standalone Maestro tool under
`Shattered-AI/tools/mobile-test` can install the app on the (already-scriptable) Android
emulator, drive it through login → push registration → an admin sending an announcement,
and capture screenshots proving the whole loop works — mirroring how
`Shattered-AI/tools/browser-test` already does this for web. Reached when step 7's live
end-to-end Maestro run produces a showcase screenshot of the announcement actually
landing in the emulator's notification shade.

## Constraints

- **Android only, everything, this pass.** iOS is explicitly out of scope — do not
  touch `/workspace/shatteredarchive-mobile/dsl-client/ios/` or
  `dsl-client/plugins/withoutPushEntitlement.js`. Confirmed with the user twice: once
  for push specifically (free "Personal Team" signing can't provision the entitlement),
  once for Analytics/Crashlytics too (no Mac/Xcode available to build-verify iOS
  changes here).
- `android/` and `ios/` are **committed, hand-maintained native folders** — no script in
  the normal build/run/deploy cycle (`start-android.js`, `build-android.js`,
  `build-apk.js`, `package-apk.js`) re-runs `expo prebuild`. Android Firebase wiring
  must be done by **hand-editing the committed Gradle files directly** — do not rely on
  an Expo config plugin taking effect.
- There is **no automated deploy/restart pipeline** for Server.Web.Public (manual
  `docker compose up --build -d` by an operator, no `IHostApplicationLifetime` hook
  anywhere in `Program.cs`). The restart notice is therefore an **admin-triggered manual
  broadcast**, not an automatic hook — do not attempt to wire an automatic
  shutdown-signal-driven notification.
- The Firebase service-account key for server-side sending **cannot be generated by
  Claude** — it's a manual download from the Firebase Console the user must provide.
  Design around its absence gracefully (fail fast with a clear error) rather than
  blocking earlier steps on it.
- **Announcements are gated by the hub-delegated Owner/Admin tier ladder
  (`ServiceTiers`/`ServiceRoleStore`), not the older site-wide `[AuthorizeAdmin]`
  attribute.** Those are two different role systems in this codebase (see Context) —
  using the wrong one would either lock out real Owners or let in accounts the user
  didn't mean to include. Both sending AND listing past announcements are Owner/Admin
  only — reading the audit trail is not open to everyone the way
  `ServiceRolesController.List()` is.
- Follow ShatteredArchive's dependency-security rules for the new native RN packages
  (pnpm via Corepack, `--frozen-lockfile` in scripts, allowlist any blocked post-install
  build script in `onlyBuiltDependencies`/`allowBuilds` if pnpm flags one).
