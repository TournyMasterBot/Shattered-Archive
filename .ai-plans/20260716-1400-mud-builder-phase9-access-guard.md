# Plan: MUD Builder — Phase 9 (builder access guard + change audit)

Created: 2026-07-16T14:00:00Z · Workspace: /workspace/shattered-archive · Status: COMPLETE
Task: Put an access guard in front of the deployed builder (build.shatteredarchive.dev currently accepts writes from anyone who can reach it) with a full token lifecycle — a per-install service master key generated on first run, UI-managed API keys (create / revoke / rotate) — and record an audit trail of every disk-mutating request.

## Goal
Every mutating builder request (PUT/POST/DELETE on areas, reload, skills, groups) requires a valid bearer credential: either the service master key (generated by the server on first run, never in the repo — every install gets a different one) or an API key created from it through the UI. API keys can be listed, created, revoked, and rotated in the UI; master-key and API-key requests flow through the SAME Authorization: Bearer scheme, with key management gated to the master key only. Every accepted mutation and every key-lifecycle event appends one line to an audit log. Done when the deployed stack rejects an unauthenticated PUT via the edge, an API key minted through the flow succeeds, a revoked key gets 401, a rotated key's old value gets 401 while the new one works, the audit lines appear, and all suites stay green.

## Constraints
- STABILITY IS KING; the MUD itself is untouched this phase (no C changes, no game deploys). Only the builder pair changes; edge config untouched.
- Reads stay open (GET /api/*, the UI itself) — the guard protects WRITES (all non-GET /api/*); preview/download of stock data stays usable without a token.
- Master key: generated by the SERVER on first run (crypto.randomBytes), persisted to `<areaPath>/backups/builder-auth.json` on the existing bind mount so it survives container recreation. That file must be git-ignored in merc-mud (NOTE: `2.4/area/backups/` is a TRACKED directory there — add an explicit `builder-auth.json` entry to /workspace/merc-mud/.gitignore; `*.log` already covers audit.log). The key value must NEVER appear in any tracked file of any repo.
- API keys are stored HASHED (sha256) at rest; the plaintext is returned exactly ONCE at create/rotate time. The master key is stored plaintext in the git-ignored auth file (single-operator project; the operator reads it from the host bind mount).
- Consistent flows: one bearer scheme for everything; master key authorizes key management AND mutations; API keys authorize mutations only; revocation/rotation take effect immediately (no caching of validity).
- Audit lines never contain token values — key id + label only.
- Auth is active when MUD_WRITE_ENABLED=true (the only deployment that can mutate disk); when writes are disabled the guard is off and behavior is unchanged (local dev). Env escape hatch MUD_BUILDER_AUTH=off for local write-mode testing only, never set in the deployed compose.
- Never break the E2E drivers: they read the master key from the auth file via the host bind mount, not hardcoded.
- All code testable in isolation; same never-crash server contract.
- qwen (container) must NOT run pnpm install|build|test; JS verification is a host job.
