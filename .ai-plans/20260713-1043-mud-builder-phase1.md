# Plan: MUD Builder — Phase 1 (app scaffold, Merc 2.4 area bridge, hot reload)

Created: 2026-07-13T15:43:47Z · Workspace: /workspace/shattered-archive · Status: COMPLETE
Task: Scaffold apps/mud-builder-client + apps/mud-builder-server, build a lossless TypeScript parser/emitter for the Merc 2.4 `.are` format, and add a hot-reload mechanism to merc-mud so saved edits reach the running game.

## Goal
A builder can run `pnpm --filter mud-builder-server dev` + `pnpm --filter mud-builder-client dev` locally, browse the areas of `/workspace/merc-mud/2.4/area`, edit a room in a React UI (forms primary; raw-code editing allowed but clearly flagged), PREVIEW the exact generated file text, DOWNLOAD it, and — only when disk writes are explicitly enabled — save it back in byte-faithful Merc 2.4 format and hot-reload the running merc-mud in place with ZERO downtime (no reboot, no dropped or frozen connections). Done when the round-trip test suite passes over every shipped `.are` file and one end-to-end edit→preview→save→live-reload cycle is demonstrated against the local merc-mud docker instance with players connected throughout.

## Constraints
- Local execution only this phase. Docker image, compose service, nginx `build.` subdomain wiring is a LATER phase (deploy/docker-compose.shattered-archive-experimental.yml) — do not touch deploy/ now.
- STABILITY IS KING (core project tenet, applies to ALL generated code): the running MUD must NEVER go offline as a result of builder actions — no dropped player connections; reload paths must never leak memory (every replaced string goes through free_string; never orphan allocations); must never crash or let an error escape (every failure path is caught, reported to the invoker, and leaves the world state untouched — two-phase validate-then-commit everywhere).
- TWO reload tiers, both required: (1) **hot reload** (in-place upsert, step 6) is the routine path — zero interruption of any kind; (2) **copyover** (step 7) is the true-fresh-slate warm reboot — connections preserved across execv but with a brief world freeze — used as the RECOVERY/fallback path when hot reload reports errors, when deletions must actually take effect, or when accumulated state is suspect. Copyover is never the routine reload; hot reload is never trusted as the only recovery.
- UI editor is the PRIMARY interaction; every edit surface must offer a PREVIEW of the exact code/text that will be written before anything touches disk, plus DOWNLOAD of the generated output. Direct raw-code modification is allowed but must be clearly marked/flagged in the UI and in the saved provenance (which fields were hand-edited vs form-generated).
- Disk writes to the MUD folders are GATED: `MUD_WRITE_ENABLED=true` only when deployed via the experimental compose file (a later phase sets it there); local dev defaults to preview/download only. For local staging verification against merc-mud the flag may be set explicitly and deliberately — never by default.
- All code must be testable/verifiable in isolation: TS packages are pure/mockable with co-located tests; the C reload module lives in its own file with its logic factored so validate/commit can be exercised without a live socket loop.
- Same stack and conventions as the existing app pairs (TypeScript, React, Vite, Express-style server, pnpm via Corepack, `--frozen-lockfile`). Port convention: game=31000, web=41000, kingdom-tactics=51000 → **mud-builder-server=61000**.
- Emitted area files MUST load in unmodified `db.c` — the emitter targets the exact Merc 2.4 on-disk grammar, not a prettified variant.
- Never edit `/workspace/merc-mud/2.4/area/*.are` destructively: writes go through atomic write + timestamped backup.
- `-server`/`-client` packages need their own local `jest.config.cjs` (root jest config does not collect co-located tests — see kingdom-tactics-server precedent).
- qwen (container) must NOT run `pnpm install|build|test` — JS verification is a host job; qwen steps end at "transcribed, ready for host verify".
- Skills/spells/songs live in C tables (`const.c` skill_table), NOT data files — editing those needs C codegen or a data-driven refactor and is explicitly DEFERRED to a later phase. Phase 1 scope: areas (rooms, mobs, objects, resets, shops, specials, helps) + the hot-reload transport.

### [x] 6. (CLAUDE) merc-mud ZERO-DOWNTIME in-place area reload (validate-then-commit upsert)
- Do: In /workspace/merc-mud/2.4/src add a new self-contained module `area_reload.c` implementing `reload_area(const char *filename)` with a strict two-phase design. **Phase A — validate:** parse the file completely into TEMPORARY structures (reusing db.c's fread helpers pointed at a staging context, never the live hash tables); ANY parse error → free all staging memory, report the error text to the invoker, live world untouched (db.c's bug()+exit paths must NOT be reachable from this path — the reload parser returns errors instead of exiting). **Phase B — commit via in-place upsert:** for each room/mob/obj prototype whose vnum already exists, free_string the old string fields and overwrite the fields of the EXISTING struct in place (so every live pointer to that prototype anywhere in the world stays valid — no dangling pointers, no downtime); brand-new vnums are allocated and hashed normally; vnums missing from the new file are left installed but logged (removal deferred — never free a possibly-referenced prototype mid-session); the area's reset list is swapped wholesale (old resets freed — they are area-owned, nothing else points at them). No reboot, no execv, no descriptor churn — players never notice except the content changing. Keep the change additive (GMCP bolt-on style); factor validate/commit as separate functions so each can be exercised in isolation (e.g. a `--validate <file>` CLI flag on the mud binary or a small test harness target in the Makefile).

- Do: In /workspace/merc-mud/2.4/src implement classic copyover in its own module: `do_copyover` (immortal command) writes each live descriptor's fd + character name to a recovery file, announces to players, then execv's the mud binary with a `--copyover` flag; on startup with that flag, comm.c's boot path skips the fresh-listen-only route, reopens the recovery file, re-adopts the saved fds as descriptors, and reconnects each one to its saved character (players see a brief "the world shimmers" pause, never a disconnect). Sentinel trigger: update_handler also honors `../area/copyover.signal` (written by /api/reload mode:"copyover"). Failure containment: if writing the recovery file or execv fails, abort and continue running normally (report the error) — never die trying to recover. Keep additive; factor recovery-file read/write as isolated functions.
- Files: /workspace/merc-mud/2.4/src/copyover.c (new), copyover.h (new), /workspace/merc-mud/2.4/src/comm.c (startup recover path + main arg), interp.c, interp.h, update.c (second sentinel), Makefile
