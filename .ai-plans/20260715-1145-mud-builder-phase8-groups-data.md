# Plan: MUD Builder — Phase 8 (skill groups as authorable data)

Created: 2026-07-15T11:45:00Z · Workspace: /workspace/shattered-archive · Status: COMPLETE
Task: Extend the Phase 7 data-overlay pattern to `group_table` (const.c) — the skill GROUPS that drive character creation costs and `gain`/practice bundles — so group ratings and membership are authorable from the Skills tab without recompiling.

## Goal
A builder can edit a group's per-class ratings and its member skill/group list in the UI, save, and see the change live after a copyover (e.g. a group's creation cost changes in the `customize` screen, or a spell added to a group becomes gainable with it). Done when an edited group round-trips through the deployed UI into live telnet behavior, the game boots identically when groups.dat is absent, and all suites are green.

## Constraints
- STABILITY IS KING; MUD never goes offline. Same overlay contract as skills.dat: absent/invalid file ⇒ compiled group_table, bug()+skip bad rows, NEVER exit, loader uses its own tolerant parser (stock fread_* exit(1) on bad input).
- Group NAMES are identity and immutable (player files save learned groups by name — save.c "Gr" lines — and C hardcodes group_lookup calls like "rom basics"); member entries must name EXISTING stock skills or groups (the overlay cannot invent either).
- MAX_GROUP=30, MAX_IN_GROUP applies to member lists (check merc.h for the exact cap); ratings are sh_int per MAX_CLASS=4 classes, -1 = unavailable for that class (verify the sentinel in skills.c before validating bounds — this differs from skill ratings).
- Same tenets as always: preview exact generated text, download always available, writes gated by MUD_WRITE_ENABLED, compact mb-field layout, copyover is the apply path.
- qwen (container) must NOT run pnpm install|build|test; JS/C verification is a host job.

  - **Rating sentinel semantics (verified)**: `-1` = unavailable to that class ("beyond your powers" do_gain skills.c:171-175, "not available" customize :652); `0` = free/auto — basics groups granted by hardcoded group_add at creation (comm.c:1918-1944, save.c:596-598), NOT gainable (rating<=0) and NOT purchasable (rating<1); `>0` = cost in trains (do_gain :177,186) / creation points (customize :659-670, 300-point cap). sh_int → validate rating ∈ {-1} ∪ [0,32767].
  - **CYCLE = CRASH (confirmed)**: group_add (skills.c:940-974) calls gn_add UNCONDITIONALLY at :972 even when the group is already known; gn_add loops members calling group_add. Any membership cycle (incl. self) = infinite recursion = stack overflow. Stock is acyclic. Cycle rejection is mandatory in TS validation AND the C loader (DFS over the prospective table before applying each row).
  - **Member resolution**: group_add tries skill_lookup FIRST, then group_lookup — skills shadow groups; both lookups are PREFIX matchers. Validation therefore requires members to EXACTLY equal a stock skill name (excluding row 0 "reserved") or a stock group name. Names never change so member legality can be judged against the live tables at load time (no stock snapshot needed, unlike the skills pair rule).
  - **Identity**: player files persist `Gr '<name>'` per known group (save.c:272; load :889-905 via group_lookup, unknown → bug + lost). Hardcoded names: "rom basics" + class_table base_group/default_group ("mage/cleric/thief/warrior basics/default", const.c:266-267 et al). pc_race_table bonus skills (const.c:236-247) are skill names in stock. → group NAME immutable, row identity.
  - **groups.dat format (decided)**: `V1` header; per group 2+N lines: `<name>~` / `<rat0> <rat1> <rat2> <rat3> <memberCount>` (5 ints, count 0..15) / exactly memberCount lines `<member>~`; terminator `$~`. Sparse overlay legal; builder emits the full table (27 stock groups).
