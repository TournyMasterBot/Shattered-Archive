# Plan: MUD Builder — Phase 7 (skills/spells as authorable data)

Created: 2026-07-15T08:30:00Z · Workspace: /workspace/shattered-archive · Status: COMPLETE
Task: Make skill/spell/song DATA authorable from the builder — the last non-.are authoring gap. Skills live in C tables (const.c skill_table), so this phase adds a boot-time data overlay the game reads, plus a Skills tab.

## Goal
A builder can edit a skill's numbers and strings (per-class levels/ratings, mana, beats, damage noun, wear-off messages) in the UI, save, and see the change live after a copyover — without recompiling the game. Done when an edited spell (e.g. changed mana + wear-off message) round-trips through the deployed UI into live telnet behavior, with a compiled-in fallback proving the game boots identically when the data file is absent, and all suites green.

## Constraints
- STABILITY IS KING; MUD never goes offline. The loader must be an OVERLAY with the compiled-in skill_table as fallback: data file missing/invalid ⇒ boot exactly as today (log a note, never exit). A bad row is rejected at load with a bug() line, never a crash.
- NO new spell FUNCTIONS from data — spell_fun/gsn wiring stays C. The data file references functions BY NAME through a registry mirrored from const.c; an unknown name is a validation error in the builder AND a skipped row in C.
- Slot numbers are load-bearing (objects reference spells by slot in .are files via skill_lookup on slot); the UI treats slot as read-mostly and validates collisions.
- Same tenets as always: preview exact generated text before write, download always available, writes gated by MUD_WRITE_ENABLED, compact mb-field layout, verbatim preservation of anything unlisted.
- qwen (container) must NOT run pnpm install|build|test; JS/C verification is a host job.
